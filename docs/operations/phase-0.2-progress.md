# Phase 0.2 acceptance tracker

| Acceptance item                                                       | Status                     | Evidence / remaining work                                                                                                                                                                                                                    |
| --------------------------------------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Meaningful mechanics for attack, heal, scout, strategist and sabotage | Implemented                | Attack damages the encounter; heal restores party vitality; scout advances objectives and weakens the encounter; strategist votes choose assault or retreat; sabotage trades party vitality for higher damage. Domain tests cover each role. |
| Valid sequences can reach victory and defeat                          | Implemented                | Nine default attacks can defeat the encounter; resolving without defeating it is a loss. A strategist assault vote adds a bounded finishing bonus; a retreat majority blocks victory. There is a 20-action encounter cap.                    |
| New quests reset encounter state                                      | Implemented                | Vitality, objectives, action count, votes and member contributions reset; player identities and roles persist. A three-quest domain test covers the reset.                                                                                   |
| Completed encounters update persistent world memory                   | Implemented                | Game start/resolution facts are bridged through the PostgreSQL transactional outbox, then recorded as validated world adventures and chapters. Deterministic IDs make retries idempotent. In-memory mode applies the same facts directly.    |
| Twitch EventSub IDs are durably deduplicated                          | Implemented                | `twitch_event_inbox` has a unique event ID. Inbox insertion, game events, snapshot and outbox writes share one transaction. A rollback/retry integration case is included.                                                                   |
| Game event replay and snapshot verification                           | Implemented                | `replayGameEvents` and `verifyGameHistory` rebuild state from ordered facts; the API exposes `/api/game/verify`; tests reject tampered history.                                                                                              |
| PostgreSQL repository/outbox integration coverage                     | Added, execution pending   | The integration suite covers concurrent duplicate delivery, transactional rollback, snapshot replay and outbox retry. It is skipped without `DATABASE_URL_TEST`; Docker Desktop was unavailable in this environment.                         |
| Dashboard displays actual world memory                                | Implemented                | It loads `/api/world/snapshot` and `/api/world/history`, then refreshes after encounter resolution. Hardcoded lore and win streaks were removed.                                                                                             |
| Security release gate                                                 | Guard retained; incomplete | Production startup still refuses to run without authenticated streamer sessions and scoped OBS credentials. CORS is documented as non-authentication. Production security is not accepted until those controls are implemented and reviewed. |

The public launch gate remains closed. PostgreSQL integration tests must run against a disposable PostgreSQL 17 database with `DATABASE_URL_TEST` configured before Phase 0.2 can be accepted.

To execute the database suite locally, point `DATABASE_URL_TEST` at a dedicated throwaway database (the suite creates and drops an isolated schema), then run `pnpm --filter @sidequest/persistence test`. Do not point it at production or a database with valuable data.
